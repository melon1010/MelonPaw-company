# MelonPaw-Company

> **Первый выпуск в мире · корпоративный Java «лобстер»**

MelonPaw-Company — платформа совместной работы и выполнения задач AI Agent для частного развёртывания в одной компании. Она построена на Java 17, Spring Boot WebFlux и AgentScope Java 2.0.0 GA, а консоль использует React, TypeScript и Vite. Платформа предоставляет рабочие пространства, память, Skills, MCP, инструменты, автоматизацию и отечественные каналы. «Первый выпуск в мире» — позиционирование проекта, а не независимый рейтинг или сертификация.

«Лобстер» — распространённое в китайском Agent-сообществе название формы продукта. Проект заимствует идеи Hermes Agent и других открытых Agent, но не является официальным Java-портом, форком, зависимостью, совместимой реализацией или официально одобренным продуктом Hermes Agent.

## Границы продукта

- Один экземпляр обслуживает одну компанию; это не SaaS-мультитенантность, подписка или биллинг.
- Поставляется адаптивная Web-консоль с поддержкой мобильного браузера; отдельного клиента, CLI и Coding-режима нет.
- Приложение запускается как JAR или обычный процесс. Развёртывание Kubernetes пока не предоставляется.
- Идентификаторы, роли, членство команды и личные ресурсы хранятся во встроенной SQLite; PostgreSQL не требуется.
- Поддерживаются DingTalk, Feishu, QQ, WeChat и WeCom; учётные данные канала принадлежат настроившему их пользователю.
- Локальные модели используют Ollama из среды развёртывания; приложение не устанавливает, не обновляет и не встраивает Ollama или llama.cpp.
- `/mission` использует фиксированные Native Subagent `researcher`, `executor`, `reviewer`; динамическое, вложенное и межкомандное делегирование отключено.

## Возможности

- Корпоративная аутентификация, RBAC, личные и командные Agent.
- Личные рабочие пространства, Markdown, Skills, MCP, каналы, диалоги и память.
- Члены команды и командные рабочие пространства; ресурсы командного Agent доступны разрешённым участникам.
- Потоковые SSE-диалоги, вызовы инструментов и события `tool/result`.
- Управление Agent, моделями, инструментами, MCP, аудитом, резервными копиями и системой по правам.
- Риск-ориентированные подтверждения, ограничения путей, сканирование Skill, маскирование секретов и аудит.
- Центр задач Agent, Goal и Mission с общими квотами, результатами, отменой и повтором.
- Ограничение LLM на уровне Agent: параллелизм, QPM и backoff для 429; это не заменяет корпоративные квоты.
- Файловая память AgentScope и режим отключённой памяти. ReMeLight и ADBPG не подключены к Java runtime и не показываются в настройках.
- Проверка OAuth 2.0 Client Credentials для удалённого MCP; Client Secret хранится зашифрованным.

## Языки интерфейса

Язык консоли по умолчанию — упрощённый китайский (`zh`). Пользователь может изменить сохранённое предпочтение в меню языка. Доступны китайский, английский, японский, русский, бразильский португальский, индонезийский и вьетнамский.

Перевод интерфейса охватывает React UI, компоненты дизайн-системы, даты и общие сообщения. Ответы модели, вывод инструментов, результаты MCP, загруженные файлы и тексты Skills не переводятся. Язык Agent отдельно выбирает файлы персоны `SOUL.md`, `AGENTS.md`, `PROFILE.md`, `MEMORY.md`, `BOOTSTRAP.md`, `HEARTBEAT.md`; доступные языки Skill задаёт его metadata. Теги нормализуются по BCP 47 (`zh-CN` → `zh`, `pt-PT` → `pt-BR`).

## Права, совместное использование и изоляция

Авторизация проверяет четыре слоя: корпоративный RBAC, владельца Agent, границы файлов workspace/Docker и правила риска AgentScope Permission. Меню интерфейса и переданный клиентом `X-Agent-Id` не дают права.

Командное пространство внутри использует стабильный scope `PROJECT`. «Общий» означает использование одного командного Agent, а не копирование личных данных в команду.

| Ресурс | Личный Agent | Командный Agent |
| --- | --- | --- |
| Workspace, файлы, результаты | Только владелец | Разрешённые участники Agent |
| Диалоги и история | Только владелец | По роли команды и `agents:use` |
| Долговременная память | Только Agent владельца | Общая для Agent, отдельно от личной |
| Skills и MCP | Владелец управляет | Общие, обслуживание требует права управления |
| Задачи и результаты | Только владелец | Scope `PROJECT`, проверка при чтении, отмене и повторе |
| Личные каналы и автоматизация | Только владелец | Не копируются автоматически |
| Память подтверждений | `agentId + ownerUserId + fingerprint` | Привязана к подтвердившему участнику |

Роли команды: `OWNER`, `MANAGER`, `MEMBER`, `VIEWER`. Членство не добавляет корпоративное `agents:use`. `VIEWER` читает разрешённые результаты, но не запускает и не продолжает диалог. Даже `SYSTEM_ADMIN` не получает обычный доступ к личным данным; нужен аудитируемый `data:breakglass`.

`RISK_BASED` разрешает обычное чтение, спрашивает для Shell-записи, удаления, установки, изменения прав, загрузки, деплоя и опасного MCP, а доступ к секретам, выход из workspace и явный запрет отклоняет. Запоминается только явное разрешение. Отказ, отмена, тайм-аут и постоянный отказ не запоминаются и не передаются между участниками.

Коды корпоративных прав задаются явно: `agents:use` запускает разрешённые Agent; `workspace:personal`, `skills:personal`, `mcp:personal`, `channels:personal`, `automations:personal` управляют ресурсами пользователя; `agents:manage` управляет неперсональными/командными Agent; `approvals:decide` принимает разрешённые решения; `audit:read` читает аудит; `system:manage` управляет общей инфраструктурой; `data:breakglass` даёт аудитируемый экстренный доступ. Ни один код не обходит владение, членство команды или границу workspace Agent.

В Docker-режиме файловые/командные инструменты и stdio MCP видят только подкаталог разрешённого Agent. Корень workspace, личный Agent другого пользователя и Agent другой команды не монтируются. Sandbox ограничивает процессы, сеть и файловую систему, но перед запуском всё равно проверяются корпоративный RBAC и AgentScope Permission.

## Предпросмотр файлов

Раздельный просмотр поддерживает браузерные изображения (`avif`, `bmp`, `gif`, `jpeg`, `jpg`, `png`, `svg`, `webp`), видео (`m4v`, `mov`, `mp4`, `ogg`, `webm`), аудио (`aac`, `flac`, `m4a`, `mp3`, `oga`, `wav`), PDF, DOCX, XLSX и обычные текстовые/кодовые форматы. Ограничение текста — 1 MB, DOCX/XLSX — 20 MB; сложное Office-форматирование не гарантируется.

## Совместимость с AgentScope 2.0

Используются официальные возможности provider extension/`ModelRegistry`, `RuntimeContext`, `AgentStateStore`, Harness Workspace, файловых/execute-инструментов, `DockerFilesystemSpec`, `IsolationScope.USER`, динамических Skills, `SkillManageTool`, `PermissionContextState`, `PermissionEngine`, `RequireUserConfirmEvent` и фиксированных Native Subagent Factory. Worker получает ограниченные инструменты и отдельный контекст; динамическое, вложенное и межкомандное делегирование отключено. См. [docs/AGENTSCOPE_2_ALIGNMENT.md](docs/AGENTSCOPE_2_ALIGNMENT.md).

## Структура

```text
melon-plugin-api/   SPI сторонних плагинов
melon-core/         runtime Agent, конфигурация, модели, безопасность, middleware
melon-tools/        малые расширения, например инструменты расписаний
melon-channels/     адаптеры каналов, очереди, контроль доступа
melon-app/          Spring Boot Web, аутентификация, сервисы и API
console/            React Web-консоль
docs/               архитектура, источники и публикация
```

Maven объединяет пять Java-модулей и включает `console/dist` в JAR. Отдельных CLI, Coding и desktop-модулей нет.

## Требования

JDK 17+, Maven 3.8+, Node.js 20.19+ (рекомендуется 22 LTS) и Docker для production-инструментов файлов и команд. В доверенной разработке можно использовать профиль `local` с выполнением на хосте.

## Сборка и запуск

```bash
cd console && npm ci && npm run build
cd .. && mvn clean package
docker build -t melonpaw-company-sandbox:latest docker/sandbox
MELON_EXECUTION_SANDBOX=docker MELON_SANDBOX_IMAGE=melonpaw-company-sandbox:latest \
  java -jar melon-app/target/melonpaw-company-web.jar
```

Порт по умолчанию — `8088`. Для workspace приложения задайте `MELON_WORKSPACE_ROOT`; при Java-сервисе в контейнере задайте путь хоста `MELON_SANDBOX_HOST_WORKSPACE_ROOT`. Монтируется только подкаталог разрешённого Agent, не весь root. stdio MCP по умолчанию следует Docker и управляется `MELON_MCP_STDIO_MODE=local|docker|disabled`. `MELON_SANDBOX_RUNTIME=runsc` включает gVisor и для Agent Shell, и для stdio MCP; недоступный runtime приводит к ошибке без fallback.

Локальные проекты stdio MCP должны находиться под `MELON_MCP_IMPORT_ROOTS`. После проверки они копируются по хэшу содержимого в `.melon/mcp-sources` владельца Agent, а контейнер получает только пути `/workspace/...`; исходный каталог хоста в MCP-контейнер не монтируется. Выход через symlink, смешивание roots и превышение лимитов отклоняются. Зависимости Node/Python готовятся и кэшируются в sandbox. Эта переменная относится к окружению запуска Java-процесса, поэтому после изменения требуется перезапуск; эквивалентное свойство Spring — `melon.execution.mcp.import.roots`. Если Java работает в Docker, доверенные roots монтируются read-only только в Java-контейнер; MCP по-прежнему получает лишь workspace своего Agent. Если сохранённый в консоли путь отличается от read-only пути, видимого Java, задайте `MELON_MCP_PATH_MAPPINGS` как JSON-карту префиксов, например `{ "/home/mineru/Github": "/mcp-imports" }`. Побеждает самый длинный префикс, сохранённый MCP JSON не меняется, а каждая цель должна существовать внутри `MELON_MCP_IMPORT_ROOTS`.

Если пользователей ещё нет, первого администратора можно создать напрямую без bootstrap-токена. Если endpoint инициализации доступен извне, перед запуском задайте `MELON_BOOTSTRAP_TOKEN` либо установите `MELON_GENERATE_BOOTSTRAP_TOKEN=true`, чтобы создать файл `${MELON_HOME}/bootstrap.token`. Поле токена отображается только при включённой защите. После создания первого администратора сгенерированный файл удаляется, а bootstrap навсегда закрывается. SQLite находится в `${MELON_HOME}/enterprise.db`; резервная копия включает DB, `config.yaml`, `workspaces`, но не публикует `master.key` и `bootstrap.token`.

## Модели и секреты

ID модели имеет формат `<provider>:<model>`, например `dashscope:qwen-plus` или `deepseek:deepseek-chat`. Ключи можно задать в консоли или через `DASHSCOPE_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `DEEPSEEK_API_KEY`. Ollama устанавливается и запускается средой; консоль только читает `/api/tags`, выполняет pull/delete и сохраняет `ollama:<model>`.

OAuth провайдеров не поддерживается, используйте API Key. Remote MCP поддерживает только OAuth 2.0 Client Credentials, без Authorization Code, PKCE и Dynamic Client Registration. Внешний Skill принимается только как HTTPS ZIP с `SKILL.md`; произвольные локальные пути и страницы маркетплейсов отклоняются. Секреты модели, каналов и MCP сохраняются с AES-256-GCM; можно передать `MELON_MASTER_KEY`, иначе создаётся `${MELON_HOME}/master.key`.

## Разработка и проверка

```bash
mvn -pl melon-app spring-boot:run -Dspring-boot.run.profiles=local
cd console && npm ci && npm run dev
npm run test:run
npm run build
```

Vite запускается на `http://localhost:5173`; при другом backend задайте `VITE_API_BASE_URL`. Профиль `local` использует `cmd.exe` в Windows и `sh` в macOS/Linux и предназначен только для доверенной разработки. Это точки проверки, а не утверждение, что каждое изменение уже прошло все проверки.

## Развёртывание и безопасность

Завершайте HTTPS на reverse proxy и ограничивайте порт приложения. Shell, автоматизация браузера, MCP, плагины, импорт Skills и запись файлов должны ограничиваться ролями, владельцем Agent, workspace, sandbox и подтверждениями. AgentScope Permission не заменяет корпоративный RBAC. Перед production проверьте выход из пути, обход авторизации и подтверждений, отмену процессов, восстановление backup и откат обновления.
